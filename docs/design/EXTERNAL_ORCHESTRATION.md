# 外部并行协调设计

状态：**设计储备，未实现**。未来协调器独立仓库维护，Typhon 只是候选名称。
Echidna 是后续开发主线，旧 cyber-agent 保留 core 基线；本次没有创建协调器项目。

## 1. 分工

多窗口可以作为人工启动多个独立进程的第一步；外部队列适合任务足够多、需要
认领和恢复时引入。二者可沿同一方向演进，不需要给内核加入“派发型总 Agent”。

| 边界 | 唯一责任 |
| --- | --- |
| 单个 Echidna 实例 | 一个 AgentLoop/Session；执行、局部预算、Receipt、恢复、原始事实 |
| 外部协调器 | 任务依赖、输入快照、进程/工作区分配、总预算、任务认领与结果收集 |
| 接收/验收者 | 验证目标和证据、处理冲突、决定采纳与合并；收件不代表成功 |
| 人工界面 | 看进度、纠偏和终止；不从窗口文字推断持久状态 |

当前 CLI 不是 worker/headless API，标准输出也不是机器任务协议。稳定机器入口
需要另立 Slice。不能通过改提示词或解析 `Echidna>` 冒充受支持的任务协议。

## 2. 哪些工作适合并行

- 对固定输入独立阅读不同模块、独立假设审查、独立测试与文档草案。
- 互不依赖的目标，在各自授权范围、工作区和资源上运行。
- 实现与独立只读审查可以分离，但审查必须绑定实现候选，不能在候选变化后沿用结论。

共享修改同一文件/Session、共用设备/账号/端口/远端目标、需要前一步结果的验证，
必须建立依赖或串行资源约束。现有 project writer/runtime lease 禁止同一 Project
并发 Chat；独立 Git worktree 也不隔离外部设备、网络服务或输出绝对路径。

## 3. 最小任务契约候选

这里描述语义，不提前定 JSON Schema/数据库或公开类型：

- `task_id` 标识任务，`attempt_id` 标识某次执行，二者不混用。
- 固定请求、目标/输入版本与哈希、范围、前置依赖、停止条件、预算及资源声明。
- 每次执行绑定一个独立工作目录与 Session、内核版本和能力说明。
- 结果引用实际输出/Receipt/Artifact，说明完成、失败、取消或效果未知；保留缺口。
- 结果提交幂等、候选版本可追踪；再次收件不会重复应用同一变更。

协调器记录调度事实；内核记录执行事实。不能由协调器编造取消 Receipt、填充缺失
日志，或把“子进程退出0”作为研究成功。状态协议不能取代已有证据校验。

## 4. 租约、故障与预算

租约过期只说明认领未续约，不说明执行已停止。先核对进程、后台 Job/PTY、Session
与资源状态；未知副作用不得自动重试或分发给第二个执行者。结果已持久化但确认丢失
时重发结果引用，不能重新运行任务来获取一份“成功”记录。

第一版以每任务独立隔离和保守串行冲突资源为主；以后若加入 fencing/lease token，
也只保护理解该 token 的写入端，不能假装可以阻止任意外部命令继续产生副作用。
并行配额来自协调器的总预算，内核继续执行本实例的请求准入预算；在途请求、未知
usage 与未关闭资源需要预留，不能把每 worker 上限相加后声称总成本受控。

## 5. 结果汇总

先收集为候选材料，再核对输入/目标/环境/方法与真实证据。跨 Project 的 Research
引用不能直接复制为本项目有效引用；导入要有明确 provenance 与本地校验契约。
冲突结论保留双方依据，由一个接收者选择验证实验，不能仅用投票或更长答案决胜。
代码由单一集成工作区合并并复测，审查与回滚绑定具体提交。

## 6. 演进与停止条件

1. 人工静态任务清单 → 独立目录/进程 → 明确结果文件 → 人工验收。
2. 出现重复协调成本后，开发最小显式 worker 入口与固定输出协议。
3. 任务量证明需要自动认领时，再引入单机 SQLite 队列、依赖/租约和故障注入测试。

暂不建设分布式队列、云服务、团队权限、多 Agent 内核、工作流 DSL、动态插件平台。
实测并行没有改善总耗时/质量，或资源冲突成本更高，就保留串行。
首次验收至少覆盖重复认领、租约过期仍执行、进程崩溃、结果确认丢失、总预算耗尽、
共享资源冲突和跨目标证据拒绝，不能只测正常完成。
